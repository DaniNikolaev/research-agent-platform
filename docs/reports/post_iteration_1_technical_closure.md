## 1. Executive Summary

**Итог: `PASS`.**

Три замечания закрыты, архитектура не менялась (модульный монолит, Domain → Application/Ports
→ Platform, единственный Artifact Store).

1. **Адресация.** Хранилище поддерживает три пространства — документное, запуска и
   платформенное. `document_id` больше не обязателен для артефактов запуска и платформы.
   Публикуемый контракт (`ArtifactReference` в пакете 2.1) **не расширялся**: он остаётся
   документным, поэтому все опубликованные JSON Schema побайтово те же, замороженные
   контрольные суммы не тронуты.
2. **Sidecar метаданных.** Запись переведена на staging + `fsync` + обратное чтение +
   исключительную публикацию (`os.link`) + повторную проверку опубликованного файла. Перезапись
   существующего sidecar невозможна; без жёстких ссылок — fail-closed. Введено правило
   видимости (артефакт читается только при наличии объекта **и** валидного согласованного
   sidecar) и диагностика `scan()` без автоматического «лечения».
3. **Воспроизводимость pytest.** Зафиксирована фактическая команда `uv run pytest -q`
   (**586 passed, 0 failed, 0 skipped, exit 0**), объяснено, почему в песочнице DSH появляется
   пустой `pytest-of-<user>/` (недоступный `%TEMP%` → fallback `tempfile.gettempdir()` на текущий
   каталог), добавлен `tmp_path_retention_policy = "none"` и создан `docs/development/testing.md`.

Проверки: `uv lock --check`, `pytest`, `ruff check`, `ruff format --check`, `ty check`,
`export_schemas --check`, пять CLI-команд — все exit 0. Регрессия: 526 тестов Итерации 1
сохранены, добавлено 60 новых (39 адресация + 20 атомарность/сбои + 1 переработанный).

## 3. Принятое решение по URI

| Пространство | Шаблон | Назначение |
|---|---|---|
| Документное | `artifact://documents/<document_id>/runs/<run_id>/<artifact_type>/<artifact_id>` | артефакт версии документа, созданный запуском; **единственное** в публикуемом контракте |
| Запуска | `artifact://runs/<run_id>/<artifact_type>/<artifact_id>` | трасса workflow, отчёт о запуске, результат над несколькими документами |
| Платформенное | `artifact://platform/<artifact_type>/<artifact_id>` | диагностика, справочники, платформенные отчёты |

Правила:

- пространство выводится из переданных идентификаторов (`scope_for`): документ+запуск →
  документное, только запуск → запуска, ничего → платформенное;
- `document_id` без `run_id` **отвергается** — частичной документной адресации нет;
- фиктивные идентификаторы (`unknown`, `global`, `default-document`) не создаются;
- `artifact_id` обязателен и уникален в пределах хранилища; тот же id в другом пространстве —
  конфликт;
- разбор URI (`parse_artifact_uri`) принимает только три шаблона и отвергает неизвестное
  пространство, лишние/недостающие сегменты, неверный регистр, `..`, `\`, percent-кодирование,
  абсолютные Windows/POSIX/UNC-пути.

**Почему публикуемый контракт не расширен.** `ArtifactReference` входит в неизменяемый пакет
2.1 и описывает артефакт, который всегда принадлежит документу и запуску. Расширение типа
потребовало бы новой версии пакета и сломало бы совместимость ради случаев, которых в пакете
нет. Поэтому run-/platform-артефакты адресуются внутренней `ArtifactMetadata`
(`STORE_ARTIFACT_URI_PATTERN`), а `ArtifactService.reference_for()` честно отказывается строить
публикуемую ссылку для не-документного артефакта. Решение зафиксировано в ADR-006 (пункт 8).

## 4. Обновлённые ArtifactMetadata и ArtifactStorePort

### `ArtifactMetadata` (внутренний контракт)

| Поле | Изменение |
|---|---|
| `artifact_id`, `artifact_type`, `uri`, `sha256`, `size_bytes`, `media_type`, `created_at`, `storage_backend`, `schema_version`, `metadata` | без изменений по смыслу; `uri` теперь `StoreArtifactUri` (три пространства) |
| `document_id` | стал необязательным |
| `run_id` | стал необязательным |

Валидаторы:

1. **согласованность**: URI ↔ `artifact_id` ↔ `artifact_type` ↔ `document_id`/`run_id` ↔
   пространство (несовпадение — `ArtifactScopeError`);
2. **нет физического пути**: `uri` не может содержать `\` или диск-префикс;
3. **нет секретов** в свободном блоке `metadata` (эвристика по ключам и значениям);
4. комбинации: документ (оба id), запуск (только `run_id`), платформа (ни одного).

Новое свойство `scope` возвращает пространство, выведенное из полей.

### `ArtifactStorePort`

| Метод | Статус |
|---|---|
| `put(artifact_type, artifact_id, data, media_type, document_id=None, run_id=None, schema_version=None)` | изменена сигнатура: идентификаторы стали необязательными |
| `get(reference)`, `exists(reference)`, `verify_checksum(reference)`, `get_metadata(reference)`, `open_read(reference)` | ужесточены: требуется видимость и согласованность с sidecar |
| `get_by_id`, `exists_id`, `get_metadata_by_id` | **новые**: чтение артефактов любого пространства по id |
| `list_by_run`, `list_by_document`, `list_platform` | `list_platform` **новый** |
| `scan()` | **новый**: диагностический отчёт без изменений на диске |
| `check_writable`, `close` | без изменений |

Новые типы: `ArtifactScanReport`, `ArtifactIssue`, `ArtifactIssueKind`,
`ArtifactScopeError`, `ArtifactPublishUnsupportedError`, `MAX_METADATA_BYTES`.

## 6. Атомарность записи sidecar

Последовательность `_publish_metadata`:

1. `ArtifactMetadata` уже провалидирован моделью;
2. детерминированная сериализация (сортированные ключи, UTF-8, `\n`);
3. проверка предела `MAX_METADATA_BYTES` (64 КиБ);
4. staging-файл **в каталоге метаданных** (тот же том), запись, `flush`, `fsync`;
5. обратное чтение staging: JSON → модель → сравнение с задуманным;
6. публикация `os.link(staged, final)` — атомарна, падает с `FileExistsError` при существующей
   цели;
7. обратное чтение **опубликованного** файла и повторная проверка;
8. при ошибке после публикации sidecar удаляется (файл создан этой же операцией).

Почему не `os.replace`: он молча перезаписывает существующий sidecar, что противоречит
неизменяемости. Почему не прямая запись в целевой файл: частичный JSON стал бы доступен
читателю. Если жёсткие ссылки недоступны, операция завершается `ArtifactPublishUnsupportedError`
(fail-closed), без «тихого» перехода к записи на месте.

**Честная формулировка:** публикация пары «объект + sidecar» не является единой атомарной
операцией. Атомарен каждый файл; согласованность пары обеспечивается порядком (сначала объект) и
правилом видимости — артефакт читается только при наличии обоих файлов и совпадении
id/URI/размера/SHA-256.

## 7. Обработка сбоев и orphan artifacts

| Сценарий | Поведение | Проверено тестом |
|---|---|---|
| A. Ошибка до публикации объекта | объекта нет, sidecar нет, staging удалён | `test_scenario_a_…` |
| B. Объект опубликован, sidecar нет | артефакт невидим (`exists_id` = false, `get_by_id` → `FileNotFoundError`); повтор с идентичным содержимым создаёт sidecar и не перезаписывает объект | `test_scenario_b_object_published_but_sidecar_missing`, `…_retry_never_rewrites_the_existing_object` |
| C. Ошибка при записи staging sidecar | объект цел, sidecar не опубликован, staging удалён | `test_scenario_c_failure_while_staging_the_sidecar` |
| C′. Повреждённый staging | не публикуется | `test_scenario_c_corrupt_staging_sidecar_is_not_published` |
| C″. Ошибка проверки после публикации | sidecar удалён, состояние «нет sidecar» | `test_scenario_c_post_publish_verification_failure_removes_the_sidecar` |
| D. Опубликовано | идемпотентность; другой контент → `ArtifactConflictError` | `test_scenario_d_…` |
| E. sidecar повреждён / без объекта / подменён хеш | `ArtifactIntegrityError`; `scan()` сообщает вид замечания; автопочинки нет (файл остаётся как был) | `test_scenario_e_*` |

Восстановление разрешено только в однозначном случае (объект есть, sidecar нет, содержимое
совпадает по SHA-256 и размеру, metadata валидны). Во всех остальных случаях — диагностическое
замечание и решение оператора; массовой очистки и удаления неизвестных файлов нет.

## 8. Fault injection tests

20 тестов в `tests/unit/test_artifact_atomicity.py`. Сбои моделируются `monkeypatch` приватных
методов адаптера (`_stage_bytes`, `_publish_metadata`, `_verify_sidecar`) и `os.link` — без
таймингов, без «спящих» тестов, на реальной файловой системе (`tmp_path`).

| Точка сбоя | Что проверяется |
|---|---|
| staging объекта | нет объекта, нет sidecar, нет staging-файлов |
| после публикации объекта | артефакт невидим, retry усыновляет объект, объект не перезаписан (mtime и байты) |
| перед записью staging metadata | объект цел, sidecar отсутствует |
| во время записи staging metadata (исходный staging) | контролируемая ошибка, публикации нет |
| проверка staging | повреждённый staging не публикуется |
| после публикации metadata | sidecar удаляется, состояние «невидим» |
| проверка опубликованного sidecar | удаление sidecar, отсутствие staging |
| повреждённый sidecar / без объекта / подменённый хеш | `ArtifactIntegrityError` + отчёт `scan()` |
| отсутствие жёстких ссылок | `ArtifactPublishUnsupportedError`, sidecar не создан |
| конкурентная запись (4 потока, одинаковое содержимое) | один объект, валидная пара, `scan()` чист |
| конкурентная запись (2 потока, разное содержимое) | один успех, один `ArtifactConflictError`, содержимое = победитель |

Дополнительно проверены детерминированность JSON, отсутствие `\r`, предел размера,
отсутствие секретов, отсутствие физических путей, отсутствие остаточных staging-файлов.

## 9. Проверка конкурентной записи

Две защиты:

1. **В процессе** — блокировка по `artifact_id` (`_artifact_lock`, реестр под общим `Lock`):
   `put()` сериализуется для одного id. Это делает исход детерминированным: одинаковое
   содержимое — один объект и общие метаданные, разное — ровно один победитель и один конфликт.
2. **Между процессами** — атомарность `os.link`: проигравший получает `FileExistsError`, затем
   действует правило «идемпотентно или конфликт» (для объекта) и «усыновить идентичный sidecar
   либо конфликт» (для метаданных). Блокировочного файла и распределённой блокировки нет.

**Неподтверждённое предположение (честно):** межпроцессная гонка не воспроизводилась отдельным
тестом — проверена только внутрипроцессная конкуренция (потоки) и семантика `os.link` на NTFS.
Поведение на сетевых файловых системах (SMB) и на Linux не проверялось.

## 10. Воспроизводимость pytest

**Фактическая команда и результат:**

```powershell
uv run pytest -q
# 586 passed in 9.75s
# exit code 0
```

Окружение: Windows 10 Pro 22H2 (`10.0.19045`) x64, CPython `3.13.18`, `uv 0.13.7`.
Команда запускалась без `--basetemp` — это и есть стандартный путь.

**Почему в песочнице появляется `pytest-of-<user>/`:** запись в `%TEMP%`
(`C:\Users\Danil\AppData\Local\Temp`) из песочницы запрещена, поэтому
`tempfile.gettempdir()` возвращает текущий каталог (`D:\MultiAgentPipeline\research-agent-platform`),
и pytest создаёт basetemp там. Следствие: пустой каталог в корне проекта, исключённый в
`.gitignore` (шаблон `pytest-of-*`). У владельца в обычном PowerShell `%TEMP%` доступен,
поэтому временные каталоги остаются вне репозитория.

**Что сделано, чтобы прогон не оставлял данных:** в `pyproject.toml` добавлено
`tmp_path_retention_policy = "none"` — содержимое временных каталогов удаляется после каждого
теста; после прогона `pytest-of-Danil/` пуст (0 файлов). Абсолютные пути в конфигурацию pytest
не зашиты.

**Вариант для полностью изолированного временного корня** (использовался при разработке как
страховка):

```powershell
uv run pytest -q --basetemp=D:\MultiAgentPipeline\.tooling\pytest-tmp
```

Оба варианта дают один и тот же результат по числу тестов; различается только расположение
временных файлов.

Создан `docs/development/testing.md`: стандартная команда, полный список проверок, правила
расположения временных файлов, особенности Windows, маркеры, ограничения среды.

## 13. Оставшиеся ограничения

| Ограничение | Причина / следствие |
|---|---|
| Публикуемый `ArtifactReference` остаётся документным | осознанно: расширение сломало бы неизменяемый пакет 2.1; run-/platform-артефакты живут во внутреннем контракте |
| Пара «объект + sidecar» не транзакционна | два файла; согласованность обеспечивается порядком и правилом видимости, а не атомарной транзакцией |
| Межпроцессная конкуренция не покрыта отдельным тестом | проверены внутрипроцессная конкуренция и семантика `os.link` на NTFS; SMB/Linux не проверялись |
| Нет операции удаления/починки артефактов | восстановление — решение оператора по отчёту `scan()`; массовая очистка запрещена |
| Нет распределённой блокировки | блокировка только внутри процесса |
| Без жёстких ссылок хранилище не пишет sidecar | fail-closed по требованию ТЗ; на FAT32/exFAT артефакты не сохраняются |
| PostgreSQL, ORM, миграции не созданы | вне объёма задания (OI-006) |
| Парсинг, OCR, RAG, резолвер, реальный провайдер отсутствуют | вне объёма задания; Итерация 2+ |
| `pytest-of-<user>/` в корне в песочнице DSH | ограничение среды (недоступный `%TEMP%`), не дефект проекта; исключён в `.gitignore` |

**Непроверенные предположения (явно):** поведение `os.link` на сетевых ФС и Linux; отсутствие
гонок между процессами на одной машине при одновременной записи одного `artifact_id`;
поведение хранилища при переполнении диска (моделировалось исключением, а не реальным ENOSPC).
