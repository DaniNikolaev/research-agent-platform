Четыре раздела — одиночные поля (`methodology`, `limitations`, `future_research`,

### 2.2 Четыре статуса и правила значения/подтверждения

Словарь: `found`, `not_found`, `unclear`, `not_applicable` (`$defs.status`).
Правила заданы условными конструкциями `allOf` в каждом типе поля
(`card_schema.json:221-243`, `257-284`, `299-321`) и продублированы в
`validate_card.py` человекочитаемыми ошибками.

| Статус | Требование JSON Schema v1.0 | Дополнительно в `validate_card.py` |
|---|---|---|
| `found` | `value` непустое (строка `minLength 1` / массив `minItems 1` / целое) **и** `evidence` `minItems 1` | `evidence_missing`, `value_missing_for_found` — ошибки |
| `not_found` | `value: null` (для списков допускается `[]`), `evidence: maxItems 0` | `evidence_for_empty_status`, `value_for_empty_status` — ошибки |
| `not_applicable` | то же, что `not_found` | те же проверки |
| `unclear` | **схема не накладывает ограничений** (ни на `value`, ни на `evidence`) | только предупреждение `unclear_without_evidence`, если `value` непустое, а `evidence` пуст |

Следствия, важные для переноса: `unclear` — единственный статус без машинного
контракта; различие `not_found` / `not_applicable` существует только на уровне
промпта (`prompts/agent_1a_prompt.md:210-222`) и никак не проверяется кодом.

### 2.3 Типы полей

| Тип (`$defs`) | Тип `value` | Ограничения значения |
|---|---|---|
| `textField` | `string` или `null` | `minLength 1` при `found` |
| `stringListField` | массив строк или `null` | элементы `minLength 1`; `minItems 1` при `found` |
| `yearField` | `integer` или `null` | `1500 ≤ value ≤ 2100` |

`yearField` дополнительно проверяется после схемы: значение вне диапазона даёт
ошибку `year_out_of_range` (`validate_card.py:406-416`), а `bibliography.doi` при
`found` — предупреждение `doi_format` по шаблону `^10\.\d{4,9}/\S+$`
(`validate_card.py:291`, `390-403`).

### 2.4 Evidence v1.0 и сопоставление цитат

Объект evidence (`card_schema.json:181-205`, `additionalProperties: false`):

| Поле | Тип | Обязательность |
|---|---|---|
| `page` | `integer ≥ 1` или `null` | обязательно (значение может быть `null`, но для пагинированного документа `null` запрещён кодом) |
| `section` | `string` или `null` | обязательно (значение может быть `null`) |
| `quote` | `string`, `minLength 1` | обязательно |
| `location` | `string` или `null` | опционально (позиция для TXT) |

Алгоритм проверки (`validate_card.py:437-500`, `503-637`):

| Результат | Условие | Эффект в отчёте |
|---|---|---|
| `exact` | нормализованная цитата входит в нормализованный текст страницы | `quotes_exact` |
| `fuzzy` (покрытие 1.0) | совпадение после удаления дефисов/мягких переносов из обеих строк | `quotes_fuzzy`, предупреждение **не** выдаётся |
| `fuzzy` (< 1.0) | покрытие `difflib` ≥ `validation.quote_check.fuzzy_threshold` (0.90) в окне от 60 символов до опорного фрагмента и до 120 символов после его конца | `quotes_fuzzy` + `quote_fuzzy_match` |
| `missing` | покрытие < 0.90 | `quotes_missing` + `quote_not_found` (+ `quote_on_other_page`) |

Нормализация (`common.fold_for_match:439-464`): регистр, пробелы, переносы через
дефис, дефисы/кавычки, лигатуры, мягкий перенос, похожие по начертанию знаки
препинания. Покрытие — сумма длин всех совпавших блоков, делённая на длину цитаты
(`_coverage:424-434`), а не один самый длинный блок. Границы страниц: проверяется
`1 ≤ page ≤ max_page`, где `max_page` — максимум из **фактически извлечённых**
страниц, а не из `source.total_pages` (`validate_card.py:515-519`, `544-550`);
расхождение с `total_pages` карточки не проверяется. Длина цитаты: пороги
`min_quote_chars = 12` и `max_quote_chars = 1200` (`settings.yaml:79`, `83`) против
«примерно 15–300 символов» в промпте (`agent_1a_prompt.md:137-138`).

перезаписывается значением из карточки (`process_documents.py:458-465`), то есть
хранит статус карточки, а не извлечения.

**Статусы запуска.** Внутренние: `pending`, `prepared`, `success`, `failed`,
`validation_failed`, `needs_repair`, `awaiting_agent`; в отчёте — `SUCCESS`,
`FAILED`, `VALIDATION_FAILED`, `NEEDS_REPAIR`, `AWAITING_AGENT`
(`process_documents.py:549-557`). Коды возврата `finalize`: `0` — успех; `1` — есть
`failed`/`validation_failed`/`awaiting_agent`; `4` — есть `needs_repair`
(`537-541`); необработанная `Agent1AError` — код `2`.

**Цикл исправления.** `validation.max_repair_attempts: 2` (`settings.yaml:72`).
При непройденной валидации пишется `repair_<document_id>_<n>.json` и печатается
команда `finalize --repair-attempt N` (`process_documents.py:362-391`, `521-530`).
После исчерпания карточка получает `validation_failed`, сохраняется в
`output/json/_failed/`, Markdown не создаётся. Существенная деталь: номер попытки
не выводится из состояния документа, а задаётся параметром CLI (`--repair-attempt`,
строка `719`); `entry["repair_attempts"]` только записывается в манифест.

### 2.6 Правила физической пагинации

| Правило | Реализация |
|---|---|
| Формат маркера | `========== PAGE {page} ==========` (`common.py:22`), разбор по `^=+\s*PAGE\s+(\d+)\s*=+$` (`common.py:24`) |
| Нумерация | физическая страница PDF с 1; собственная нумерация статьи («с. 145») игнорируется (`agent_1a_prompt.md:45-52`) |
| TXT без пагинации | маркер `========== DOCUMENT TEXT ==========` и `page = null`, позиция — в `location` |
| `total_pages` | из заголовка `TOTAL_PAGES`; при наличии страниц берётся `max(заголовок, максимальный номер)` (`common.py:368-375`) |
| Валидация | `page` обязателен для пагинированного документа (`page_missing_for_paginated`), `page < 1` → `page_invalid`, `page > max_page` → `page_out_of_range` |
| Фрагменты | страницы не разрываются, маркеры `PAGE N` сохраняются в `<id>_chunks/part_NN.txt` |

### 3.1 Дополнительно найденные ограничения качества

1. **Наличие цитаты ≠ смысловая поддержка.** Проверяется присутствие фрагмента на
   странице, а не корректность интерпретации; ложноположительное подтверждение
   возможно по замыслу.
2. **Мягкое сопоставление может простить потерю смысла.** Порог 0.90 по сумме
   совпавших блоков допускает высокое покрытие при перестановке слов или выпадении
   отрицания («не значим» против «значим»); код такие случаи не различает.
3. **`quote_language_mismatch` работает только для английских документов**
   (`doc_language == "en"`, `validate_card.py:569`): английская цитата в русской
   карточке предупреждения не вызовет.

## 6. Риски миграции

1. **Дрейф контракта v1 ↔ v2.** Влияние: старые карточки перестают читаться или
   читаются неверно. Снижение: замороженная копия схемы с SHA-256, тест
   `test_legacy_compat.py`, протокол `Agent1ACardV1ToV2Adapter`, который вместо
   выдуманных значений возвращает `MISSING_METADATA`.
2. **Ложное чувство качества от технической валидации.** Влияние: «валидный
   пакет» воспринимается как «верная карточка». Снижение: закрытое перечисление
   `SemanticVerificationStatus` без `verified`, обязательная независимая проверка
   агентом 1B и человеком, чек-лист как отдельный артефакт.
3. **Качество OCR неизвестно.** Влияние: карточки по сканам могут быть
   правдоподобно неверными. Снижение: измерить на размеченной выборке до
   включения в поток, фиксировать `extraction_method = ocr` и `needs_human_review`.
4. **Семантика пагинации для TXT.** Влияние: `null`, `1` и отсутствие страницы
   трактуются по-разному в коде и отчётах. Снижение: правило «`page_count = null`
   только для `text/plain`» и запрет `page` у evidence для таких документов.
5. **Provenance старых карточек невосстановим задним числом.** Влияние: нет
   `source_sha256`, `run_id` модели, `block_id`, `char_span` — полноценный v2-пакет
   из legacy-карточки не собрать. Снижение: не имитировать метаданные, отдавать
   `MISSING_METADATA`, использовать старые карточки только как справку.
6. **Legacy-артефакты как «золотые данные» без арбитража.** Влияние: 37/37 и 35/29/6
   легко принять за эталон качества, хотя это техническое совпадение цитат на
   синтетических фикстурах; `working/` не версионируется. Снижение: арбитраж
   человеком, фиксация расхождений, запрет на demo-числа как метрику качества.
7. **Ограничения Windows-окружения.** Влияние: кириллица и пробелы в путях,
   кодировки TXT (`cp1251`, `koi8-r`), `Tesseract` в `PATH`, блокировки файлов
   (в `tests/base.py:33-38` описан удерживаемый дескриптор PDF), регистронезависимая
   файловая система. Снижение: `artifact://` URI вместо путей, явные кодировки и
   путь к бинарнику, прогон CI в целевом окружении.

## 8. Вопросы, которые не удалось подтвердить статически

1. **Реальное качество OCR для RU/EN.** В артефактах нет ни одного документа с
   `ocr_used = true`; ветка успешного OCR не покрыта тестами, Tesseract в среде
   отсутствовал. Числа точности распознавания неизвестны.
2. **Фактическое поведение модели и его разброс.** Промпт и карточки прочитаны, но
   ни один прогон модели не наблюдался: не подтверждены устойчивость к длинному
   промпту (450 строк), частота пропусков полей, склонность к переводу цитат,
   вероятность JSON в обёртке. Всё это — гипотезы о риске (D3, §6).
3. **Получены ли демо-результаты чек-листа тем же промптом.** Числа 37/37 и
   35/29/6 совпадают с манифестом `run_20261105_231456_0643`, но в чек-листе не
   указаны `document_id` и версия промпта; тождество прогонов не доказано.
4. **Соответствие нумерованных прогонов проверенным артефактам.** В
   `working/processing_logs/` два манифеста, карточек три; карточка
   `elibrary_maksimovaiv_tsifrovizatsiya_a772367b` относится ко второму прогону.
   Полная история прогонов не восстановима: часть каталогов могла быть перезаписана,
   а `working/` не версионируется.
5. **Производительность и стоимость.** Замеров времени, токенов и стоимости нет;
   порог разбиения задан в символах (120 000), лимит контекста модели не учитывается.
6. **Происхождение ссылок «D1–D9» в ТЗ.** Реестр восстановлен из расшифровки
   предыдущей аудиторской сессии; исходный документ с этими номерами не входит в
   состав репозитория и не проверялся. Нумерация сохранена для преемственности,
   но её авторитетность вне этой сессии не подтверждена.
7. **Спецификация миграции.** `docs/migration/v1_to_v2_mapping.md` создана в этой же
   итерации (после настоящего аудита), поэтому её содержание основано на §2–§5 этого
   документа. Отдельно не подтверждено, что какое-либо legacy-хранилище (архив запуска,
   журнал, git-тег) сохраняет метаданные, необходимые для v2-пакета: `source_sha256`,
   `run_id`, `prompt_version`, `model_id`, `block_id`, `char_start`/`char_end`,
   `match_status`. Без них полная миграция старых карточек невозможна (см. §5, §6).
