# Artifact Store: адресация, атомарность и диагностика

**Дата:** 2026-11-12 (обновлено после технического закрытия) · **Основание:** ADR-006, техническое закрытие после Итерации 1 · **Код:** `application/ports/artifact_store.py`, `platform/artifact_store/{local_file_store,paths,metadata}.py`, `application/services/artifact_service.py`

Хранилище владеет отображением «логический `artifact://` URI → физическое расположение».
Порт не отдаёт вызывающему коду физический путь: только байты, поток и метаданные.
Метаданные — понятие уровня хранилища, намеренно отдельное от публикуемого
`ArtifactReference`: ссылка входит в неизменяемый пакет 2.1 и не может расти полями и
пространствами адресации, а хранилищу нужны связи с документом, запуском и версия схемы.

---

## 1. Три пространства адресации

| Пространство | URI | Когда используется |
|---|---|---|
| Документное | `artifact://documents/<document_id>/runs/<run_id>/<artifact_type>/<artifact_id>` | артефакт относится к версии документа и конкретному запуску; **единственное**, что попадает в публикуемый `ArtifactReference` |
| Запуска | `artifact://runs/<run_id>/<artifact_type>/<artifact_id>` | артефакт относится к запуску, но не к одному документу: трасса workflow, отчёт о запуске, результат операции над несколькими документами |
| Платформенное | `artifact://platform/<artifact_type>/<artifact_id>` | артефакт не привязан ни к документу, ни к запуску: диагностика платформы, справочники, платформенные отчёты |

Пространство выводится из идентификаторов, которые передал вызывающий
(`scope_for`): документ + запуск → документное; только запуск → запуска; ничего →
платформенное. **Частичная документная адресация запрещена**: `document_id` без `run_id`
отвергается, потому что у опубликованного URI нет формы «документ без запуска», а
фиктивные идентификаторы (`unknown`, `global`) не создаются.

`artifact_id` обязателен и уникален в пределах хранилища; идентификатор из другого
пространства с тем же `artifact_id` — конфликт, а не второй артефакт.

## 2. Публикуемый и внутренний контракты

| Тип | Роль | Пространства |
|---|---|---|
| `ArtifactReference` (`domain/runs/artifacts.py`) | публикуемый контракт, входит в пакет 2.1 | только документное (шаблон `ARTIFACT_URI_PATTERN` неизменен) |
| `ArtifactMetadata` (`application/ports/artifact_store.py`) | внутренний контракт хранилища | все три (`STORE_ARTIFACT_URI_PATTERN`) |

Следствие: `ArtifactService.reference_for()` отказывается строить публикуемую ссылку для
run- и platform-артефакта — такой артефакт читается по `artifact_id`, а не втискивается в
форму, которой у него нет. Публичные схемы Итерации 0/1 при этом **не менялись**:
`tools/export_schemas.py --check` подтверждает побайтовое совпадение, замороженные
SHA-256 не тронуты.

## 3. Проверки URI

`parse_artifact_uri` принимает только три утверждённых шаблона и отвергает:

- неизвестное пространство (`artifact://unknown_scope/...`);
- неверное число сегментов;
- недопустимые символы (верхний регистр, `_` в типе, пробелы);
- `..` (traversal), обратный слэш, percent-кодирование;
- абсолютные Windows-пути (`C:\...`), UNC (`\\server\share`), POSIX-пути (`/var/...`);
- URI без схемы `artifact://`.

Дополнительно `ArtifactMetadata` проверяет согласованность: URI ↔ `artifact_id` ↔
`artifact_type` ↔ `document_id`/`run_id` ↔ пространство. Несовпадение —
`ArtifactScopeError`. Метаданные также не могут содержать физический путь и не могут
нести секретоподобные значения в свободном блоке `metadata`.

## 4. Физическая раскладка

```text
<root>/
├── sha256/
│   └── <aa>/<artifact_id><ext>     неизменяемые объекты, шардированные по хешу
├── metadata/
│   └── <artifact_id>.json          sidecar метаданных
└── tmp/                            область подготовки объекта
```

- `<root>` = `paths.data_root` / `paths.artifact_subdir` (по умолчанию `data/artifacts`),
  разрешённый от корня проекта; физический корень строится из `paths`, а не из
  `storage.artifact_root_uri`.
- `<ext>` выводится из `media_type` (`.pdf`, `.json`, `.txt`, …), неизвестный тип → `.bin`.
- Sidecar — единственное место, связывающее артефакт с запуском и документом; листинг по
  run/document не читает содержимое объектов.

## 5. Видимость артефакта

Артефакт считается доступным через публичный интерфейс только при наличии **всех** условий:

1. объект существует;
2. sidecar существует и проходит валидацию;
3. `artifact_id` и `uri` в sidecar совпадают с запросом;
4. размер объекта совпадает с `size_bytes`;
5. SHA-256 объекта совпадает с записанным.

Объект без sidecar — остаток сбоя, а не артефакт: `get_by_id`/`get` возвращают
`FileNotFoundError`, `exists_id` → `False`. Sidecar без объекта — `ArtifactIntegrityError`.

## 6. Публикация: два файла, атомарность каждого

Объект и sidecar — два отдельных файла, поэтому публикация пары **не является** одной
атомарной операцией. Порядок:

```text
STAGING OBJECT → PUBLISH OBJECT → STAGING METADATA → PUBLISH METADATA → ARTIFACT VISIBLE
```

**Объект.** Байты пишутся во временный файл в `tmp/` на том же томе, выполняется
`flush` + `fsync`, размер сверяется с ожидаемым, затем публикация без перезаписи:
`os.link(staged, final)` — атомарная операция, которая падает с `FileExistsError`, если
цель существует. Fallback для файловых систем без жёстких ссылок — создание целевого файла
с `xb` и копирование; частично скопированный объект невидим, потому что видимость требует
валидного sidecar.

**Sidecar.** Последовательность строже:

1. модель `ArtifactMetadata` валидируется до записи;
2. сериализация в детерминированный JSON (сортированные ключи, UTF-8, завершающий `\n`);
3. проверка предела размера (`MAX_METADATA_BYTES` = 64 КиБ);
4. staging-файл в **каталоге метаданных** (тот же том), запись, `flush`, `fsync`;
5. обратное чтение staging-файла: JSON → модель → сравнение с задуманным;
6. публикация `os.link` без перезаписи;
7. обратное чтение **опубликованного** файла и повторная проверка.

Поведение при сбоях:

- ошибка до публикации → sidecar отсутствует, артефакт невидим, staging удалён;
- ошибка после публикации → sidecar удаляется (файл создан этой же операцией), состояние
  возвращается к «нет sidecar»; чужие файлы не трогаются;
- конкурентная публикация → `FileExistsError`; если существующий sidecar идентичен
  задуманному, он «усыновляется» (операция успешна), иначе — `ArtifactConflictError`;
- файловая система без жёстких ссылок → `ArtifactPublishUnsupportedError` (fail-closed).
  Запись sidecar «на месте» запрещена: читатель мог бы увидеть частичный JSON.

## 7. Неизменяемость и идемпотентность

| Ситуация | Поведение |
|---|---|
| тот же `artifact_id`, те же байты и то же пространство | идемпотентно: возвращается существующая метадата, файл не переписывается |
| тот же `artifact_id`, другие байты | `ArtifactConflictError` |
| тот же `artifact_id`, другое пространство | `ArtifactConflictError` |
| объект существует без sidecar, содержимое совпадает | «усыновление»: sidecar создаётся, артефакт становится видимым |
| объект существует без sidecar, содержимое другое | `ArtifactConflictError`, объект не перезаписывается |

## 8. Конкурентная запись

Внутри процесса запись по одному `artifact_id` сериализуется блокировкой из реестра
(`_artifact_lock`): две операции с одинаковым содержимым дают один объект и согласованные
метаданные, две операции с разным содержимым — ровно один победитель и один
`ArtifactConflictError`. Между процессами защита опирается на атомарность `os.link`:
проигравший получает `FileExistsError`, и далее действует правило «идемпотентно или
конфликт». Блокировочный файл не используется — распределённой блокировки в Итерации 1 нет.

## 9. Диагностика (`scan`)

`ArtifactStorePort.scan()` возвращает `ArtifactScanReport` и **ничего не исправляет и не
удаляет**. Виды замечаний:

| Вид | Значение |
|---|---|
| `object_without_metadata` | объект без sidecar (в том числе мусорное имя) |
| `metadata_without_object` | sidecar без объекта или с другим размером |
| `corrupt_metadata` | sidecar не парсится или не проходит модель |
| `sha_mismatch` | хеш объекта не совпадает с метаданными |
| `size_mismatch` | размер объекта не совпадает с метаданными |
| `uri_mismatch` | объект лежит не по тому хеш-пути, который адресуют метаданные |

Автоматическое восстановление разрешено только для однозначного случая: объект есть,
sidecar отсутствует, повторная операция предъявляет то же содержимое (SHA-256 и размер
совпадают), метаданные валидны. Во всех остальных случаях — диагностическая ошибка и
решение оператора. Массовая очистка и удаление неизвестных файлов не выполняются.

## 10. Пределы и безопасность

- `artifact_id`, `document_id`, `run_id` проверяются регулярными выражениями до любой
  файловой операции; итоговый путь разрешается и проверяется на принадлежность корню
  (`ArtifactStorePaths.contained`).
- Максимальный размер sidecar — 64 КиБ; метаданные не хранят содержимое документа и
  секреты (валидатор отвергает секретоподобные ключи и значения).
- Абсолютные пути и `..` не проходят ни в URI, ни в идентификаторах.
- `check_writable()` проверяет доступность хранилища, не создавая артефактов.

## 11. Что не реализовано

- нет распределённой блокировки между процессами и машинами (только атомарность ссылок);
- нет операции «удалить/починить артефакт»; восстановление — ручное решение по отчёту `scan`;
- нет S3-совместимого адаптера (интерфейс к этому готов);
- нет сжатия, шифрования и ротации артефактов.
