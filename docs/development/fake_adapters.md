# Fake-адаптеры модели

**Дата:** 2026-11-12 · **Основание:** Итерация 1, ADR-005 · **Код:** `platform/models/fake_model_adapter.py`,
`config/models.example.yaml`, `agents/agent_1a/graph/nodes.py`

Fake-адаптеры существуют не «для тестов», а потому что платформа обязана запускаться **без
провайдера**. Провайдер — открытое решение владельца (`OI-001…OI-004`), реальный адаптер отложен;
пока его нет, `platform check` и `agent1a workflow-smoke` должны быть исполнимыми командами, а не
описанием. Fake-адаптеры — это исполнимый путь Итерации 1.

**Явное утверждение:** fake-профиль — **не** production-конфигурация. Он детерминирован, работает
офлайн и структурно не способен произвести научное содержание: его «структурированный ответ» —
фиксированный технический объект, эхом повторяющий запрос.

---

## 1. Состав

| Класс | Реализует | `is_fake` | Особенности |
|---|---|---|---|
| `FakeChatModel` | `StructuredOutputModelPort` | `true` | текст `FAKE MODEL OUTPUT - no scientific content`; payload по умолчанию `{"ok": true, "fake": true}`; `latency_ms=1.0` |
| `FakeEmbeddingModel` | `EmbeddingModelPort` | `true` | векторы выводятся из длины текста, размерность по умолчанию 8 |
| `FakeReranker` | `RerankerPort` | `true` | убывающие оценки `1.0 − 0.1·i`; `provider_id=fake_provider`, `model_id=fake_reranker_1` |
| `FakeModelGateway` | `ModelGatewayPort` | `true` | резолвит именованный профиль в адаптер, отказывает неизвестному профилю |

Константы: `FAKE_PROVIDER_ID = "fake_provider"`, `FAKE_TEXT = "FAKE MODEL OUTPUT - no scientific content"`.
`capabilities_from_profile(profile)` переводит `ModelProfileSettings` в provider-neutral
`ModelCapabilities`; именно так профили из `config/models.yaml` попадают в gateway.

## 2. Детерминизм и офлайн

- Ни один адаптер не открывает сокет, не читает ключ и не требует сети: в модуле нет ни HTTP-клиента,
  ни SDK провайдера, ни `api_key_env`.
- Вывод chat-модели фиксирован: либо `text`, либо `payload` (оба задаются при сборке), плюс
  `finish_reason=STOP` и предупреждение `fake adapter: no real provider was called`.
- Векторы эмбеддингов детерминированы по содержимому: `((len(text) + i) mod 7) / 7` для
  `i` в `range(dimensions)`.
- Оценки реранкера детерминированы: `1.0 − 0.1·index`, по одной на кандидата.
- Не детерминировано только `created_at` у `EmbeddingResponse` (`datetime.now(UTC)`), поэтому два
  ответа с одинаковым входом не совпадут побайтово; содержательная часть воспроизводима.
- Каждый адаптер пишет полученные запросы в `calls` (диагностика и тесты); gateway агрегирует их
  в `FakeModelGateway.calls`.

## 3. Capability gate: отказ до вызова

`generate_structured` первым делом вызывает `require_structured_output(capabilities)` и падает с
`ModelUnsupportedCapabilityError`, если профиль не объявляет structured output. Это не
формальность: обнаружить отсутствие capability **после** вызова значит постфактум разбирать
свободный текст, что архитектура запрещает.

`FakeModelGateway.embed` проверяет `supports_embeddings` профиля и при отсутствии capability
бросает `ModelUnsupportedCapabilityError` — тихий откат на «похожую» модель не предусмотрен.
Неизвестное имя профиля — тоже `ModelUnsupportedCapabilityError` со списком настроенных профилей:
опечатка в имени не должна выглядеть как рабочая конфигурация.

## 4. Скриптовые ошибки

| Механизм | Поведение |
|---|---|
| `FakeChatModel(scripted_errors={task: exc})` | при запросе с этим `task` бросается нормализованная ошибка; ключ `"*"` срабатывает на любой task |
| `FakeChatModel.raise_scripted(task, exc)` | добавить ошибку после сборки |
| `FakeModelGateway(scripted_errors=...)` | раздаётся всем созданным chat-моделям |
| `FakeModelGateway.raise_scripted(task, exc)` | добавляет ошибку всем chat-моделям |
| `scripted_service_errors()` | готовый набор: `timeout`, `rate_limit`, `invalid_response` |

Исключения проходят через `normalize_provider_error`, то есть попадают в нормализованную
иерархию `ModelError` с `code` и `retryable`. Именно поэтому на них можно проверить политику
повторов графа: `timeout` и `rate_limited` повторяемы, `unsupported_capability` — нет.

## 5. Токены: синтетика без стоимости

`FakeChatModel._usage` считает «токены» из длины строк:

```text
input_tokens  = сумма длин сообщений // 4
output_tokens = max(1, длина ответа // 4)
```

`cost_usd` не заполняется вовсе: реального провайдера нет, тариф выдумывать не из чего.
Числа попадают в событие `fake_model_request_completed` как `input_tokens`/`output_tokens` и
служат меткой работоспособности связки, а не измерением.

## 6. Событие журнала

Адаптеры ничего не логируют: журнал — дело узла графа. Узел `execute_smoke_step` после успешного
вызова пишет `fake_model_request_completed` с полями `provider`, `model_id`, `attempt`,
`input_tokens`, `output_tokens`, `latency_ms`, `fake`. Событие `model_request_completed`
зарезервировано за реальным провайдером; сейчас оно не пишется ни при каких условиях.

## 7. Почему fake-адаптеры поставляются в пакете

1. **Платформа должна запускаться без провайдера.** Иначе `platform check` и
   `agent1a workflow-smoke` требовали бы ключа, которого нет и не может быть до решения владельца.
2. **Проверяется связка, а не модель.** Smoke-прогон доказывает, что состояние, Run Manager,
   Artifact Store, журнал и LangGraph собраны правильно. Fake-ответ для этого достаточен.
3. **Явная маркировка.** `is_fake=True` у всех четырёх классов, `FAKE_TEXT` в тексте ответа,
   предупреждение в каждом ответе, `platform check` показывает `WARNING` с пометкой `FAKE`.
   Маркировка присутствует и в конфигурации профиля, и в данных ответа, и в статусе health check.

## 8. Чем отличаются от дублей в `tests/fixtures/fakes.py`

| Свойство | `platform/models/` (поставляемые) | `tests/fixtures/fakes.py` (тестовые) |
|---|---|---|
| Назначение | офлайн-рантайм для CLI и демонстраций | минимальные дубли портов для юнит-тестов |
| Маркер `is_fake` | есть у всех классов | нет |
| Профили | gateway резолвит именованные профили, неизвестный — ошибка | одна жёстко заданная capability |
| Текст ответа | `FAKE_TEXT` | `"fake answer"` |
| Payload | `{"ok": true, "fake": true}` + `schema_id` | `{"ok": true}` |
| Токены | выводятся из длины | фиксированные `10/5` и `100/40` + `cost_usd=0.0` |
| Latency | `1.0` мс | `12.5` / `42.0` / `5.0` / `3.0` мс |
| Ошибки | словарь по task + `"*"` | одно поле `raise_error` на модель |
| Эмбеддинги | 8 измерений, формула от длины | 4 измерения, `0.1·index` |
| `created_at` эмбеддинга | текущее время UTC | фиксированная строка |
| Доступность | импортируется из пакета | только внутри `tests/` |

Тестовые дубли намеренно живут в тестовом дереве: их докстринг фиксирует правило «fake не должен
импортироваться из поставляемого пакета, иначе его примут за production-возможность». Для
поставляемых fake-адаптеров это правило выполнено иначе — они нужны в рантайме, поэтому
маркируются, а не прячутся.

## 9. Ограничения и остаточный риск

- Структурированный payload **не валидируется по JSON Schema**: адаптер возвращает фиксированный
  словарь и подставляет `schema_id`. Проверка соответствия схеме — задача реального адаптера и
  валидаторов следующей итерации.
- Нет streaming, tool calling и реранка через gateway: `FakeReranker` — самостоятельный адаптер,
  в `ModelGatewayPort` метода `rerank` нет.
- `FakeChatModel` не имитирует `finish_reason=length`, content filter и частичные ответы.
- Связка «`provider: fake_provider` ⇒ `is_fake: true`» **не проверяется** валидатором: если
  вручную выставить `is_fake: false`, `platform check` покажет `PASS` для fake-провайдера. Это
  конфигурационная ошибка, которую владельцу конфигурации нужно не допускать; подмены адаптера
  при этом не происходит — всё равно работает fake.
- Fake-профиль нельзя использовать как обоснование качества: он не производит научное
  содержание, и любые «результаты» smoke-прогона относятся только к технической связке.
