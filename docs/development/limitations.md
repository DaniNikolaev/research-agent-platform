# Ограничения Итерации 1

**Дата:** 2026-11-12 · **Основание:** Итерация 1 (Platform Skeleton), ADD §22 · **Статус:** каркас
платформы исполняется; функциональной обработки документов нет

Документ честно перечисляет, чего в Итерации 1 **нет**. Это не список дефектов: большая часть
отсутствующего не входила в объём итерации. Список нужен, чтобы отчёт о работающем smoke-прогоне
не читался как отчёт о работающем извлечении.

## 2. Провайдер модели

- **Нет реального LLM-адаптера и ни одного сетевого вызова.** Работает только fake-адаптер:
  `provider: fake_provider`, `is_fake: true`.
- `api_key_env` и `base_url` валидируются, но не используются: секрет не разрешается, соединение
  не устанавливается.
- Провайдер, протокол, capabilities, лимиты контекста и фактический `model_id` не подтверждены —
  `OI-001…OI-004`. Числа в примерах конфигурации — контрактные значения, а не измерения.
- Ответ модели не проверяется по JSON Schema: проверять пока нечего.
- Бюджет токенов (`input_token_budget`) рассчитывается в конфигурации, но ни один код-путь его
  не применяет: контекст не собирается.

| SQLAlchemy-модели, миграции Alembic | нет; схемы БД не существует |
| durable-хранилище запусков | `InMemoryRunRepository`: данные исчезают с процессом, `is_durable = False` |
| durable checkpointing | `InMemoryCheckpointProvider` поверх LangGraph `InMemorySaver`: после перезапуска состояния нет, resume между процессами невозможен |

| резервное копирование и восстановление | нет; политика — `OI-006` |

Практическое следствие: после завершения процесса `platform check` или `workflow-smoke`
запусков больше нет — остаются только файлы артефактов в `data/artifacts/`.

## 4. Интерфейсы и эксплуатация

- Нет FastAPI и веб-интерфейса (`fastapi` объявлен в группе `api`, не импортируется). CLI —
  единственный интерфейс.
- Нет Docker и контейнеризации: Windows-native, ADR-010.
- Нет аутентификации, авторизации, многопользовательского режима.
- Нет многопроцессной/очередной обработки: один процесс, один запуск за раз, нет worker-ов,
  очередей и блокировок между процессами. `os.link` защищает публикацию артефакта от гонки
  внутри файловой системы, но координации между процессами нет.
- Нет канала human-in-the-loop: статус `waiting_for_human` и метод `request_human_review`
  существуют, но интерфейса подтверждения нет (`OI-007`), и ни одна CLI-команда этот статус не
  создаёт.
- Нет экспортёра журнала (OTLP/console), ротации и записи в файл: когда журнал включён, он идёт
  в `stderr`.
- Нет метрик и трейсинга.

## 6. Окружение и воспроизводимость

- **pytest в песочнице DSH требует `--basetemp` вне репозитория.** Иначе тесты с `tmp_path`
  пытаются писать внутрь рабочего дерева и упираются в ограничения доступа. Это ограничение
  среды разработки, а не тестов.
- **`uv run` без `--group parsing` синхронизирует окружение по умолчанию и может удалить пакеты
  группы `parsing`.** После такого запуска для работы с парсингом нужно снова выполнить
  `uv sync --group parsing` (зафиксировано в `dependency_baseline.md` §6.1).
- DSH — инструмент разработки и в runtime не входит: ни один модуль пакета к нему не
  обращается (ADR-001, ADR-010).
- Публикация артефактов предпочитает `os.link`; на файловой системе без жёстких ссылок работает
  запасной путь через эксклюзивное создание файла. Оба варианта исключают перезапись, но
  скорость различается.
- Контрольные цифры прогона (по подтверждению владельца): **524 теста пройдено, 0 провалено,
  0 пропущено**; Python `3.13.18`, uv `0.13.7`, langgraph `1.2.20`, pydantic `2.14.3`.
  При подготовке этой документации сборка и тесты не запускались.

## Итерация 2 — обработка документов (дополнение от 2026-11-14)

Раздел выше описывает состояние **до** Итерации 2 и оставлен без изменений: он фиксирует, чего
не было в Итерации 1. Ниже — что осталось невозможным **после** появления приёма, разбора и
Quality Gate. Итерация 2 добавила конвейер для цифровых PDF и TXT, но не сделала платформу
способной обработать произвольную научную статью.

### И2.1. OCR и сканированные документы

| Чего нет | Фактическое состояние |
|---|---|
| OCR-движок | не выбран (`OI-008` открыт), реализация `OcrEnginePort` отсутствует; `document_parsing.docling.do_ocr` принудительно `false` (конфигурация и конструктор адаптера отвергают `true`), `ocr.enabled = false` |
| поддержка сканированных PDF | только **детекция**: страница без пригодного текстового слоя получает статус `ocr_required`. Но если текста нет **во всём** документе, канонический текст пуст, и узел `build_canonical_document` завершает запуск ошибкой `the canonical text is empty` (`document_pipeline_error`, код 1) **до** Quality Gate. Вердикт `requires_ocr` достижим для смешанного документа (часть страниц с текстом) или при прямом вызове Gate. Текста не появляется ни в одном случае |
| предсказуемость на реальном скане | не проверена. Если Docling извлечёт хоть какой-то текст (колонцифру, колонтитул), канонический текст непуст и возможен `requires_ocr`; если не извлечёт ничего — запуск падает на пустом каноническом тексте (`document_pipeline_error`, код 1) раньше Quality Gate |
| Tesseract, языковые пакеты, EasyOCR | не устанавливались |
| RapidOCR | пакет `rapidocr 3.10.0` и его встроенные ONNX-веса (~30.4 MB) присутствуют **как зависимость Docling**, но OCR ни разу не запускался; выбором движка это не является |
| OCR-веса в кеше модели | не скачивались; в `~/.cache/huggingface/hub` только layout- и table-модели |
| язык(и) OCR | не проверялись ни на одном движке |

### И2.4. Проверенные и непроверенные сценарии

Проверено фактически: TXT-фикстура (вердикт `passed`, код 0) и **одностраничный цифровой PDF**
через настоящий Docling (`passed`, код 0), плюс юнит-тесты без Docling (поддельный
`SourceReaderPort`, доменные модели собираются напрямую).

Не проверено:

* многостраничные документы и документы с двумя колонками (кроме единичной пробы);
* таблицы на реальных статьях и качество ячеек;
* сканированные PDF (нет движка);
* PDF с поворотом страниц (`/Rotate`) и с разными размерами страниц;
* сноски, формулы, ссылки, колонтитулы — поведение не измерялось;
* воспроизводимость повторного разбора одного и того же PDF в двух запусках (собственная
  недетерминированность Docling не измерялась);
* `document report` для запуска, чьи артефакты созданы в другом корне проекта: команда читает
  хранилище артефактов текущего `--project-root`, поэтому «чужой» запуск не найдётся;
* реальные статьи целиком — ни одной.

### И2.8. Мусор в рабочем каталоге

После тестов и реальных прогонов Docling в корне проекта появляются каталоги, не покрытые
`.gitignore`: `ing-*` (временные каталоги тестового хелпера `tempfile.mkdtemp`) и
`torchinductor_*` (кэш компиляции torch). Они не влияют на работу, но требуют ручной уборки;
автоматической очистки нет.

### И2.9. Среда

- **`uv run` без `--group parsing` может удалить пакеты группы `parsing`** — после такого запуска
  нужен `uv sync --group parsing`. Для PDF это обязательно: без группы Docling не импортируется.
- **pytest в песочнице DSH требует `--basetemp` вне репозитория** (см. §6 выше); ограничение
  среды, а не тестов.
- DSH в runtime не входит.
- Контрольные цифры Итерации 2 (по подтверждению владельца): **619 тестов пройдено, 0 провалено,
  0 пропущено**; `ruff` — без замечаний; `ty` — 14 диагностик; экспорт схем — 10 схем актуальны.
  При подготовке этой документации сборка и тесты не запускались.
