# Контракт Evidence 2.1: кандидат модели и запись резолвера

**Версия контракта:** `2.1` · **Модели:** `EvidenceCandidate`, `EvidenceCandidateList`, `EvidenceRecord` · **Модуль:** `src/research_platform/domain/evidence/models.py` · **Дата:** 2026-11-12

Evidence — самостоятельный объект с идентификатором и локатором в источнике, а не строка
цитаты внутри карточки. Контракт 2.1 разделяет **предложение модели** и **запись,
построенную кодом**, структурно: это две разные модели с разными полями и разными правами.

---

## 1. Принцип двух объектов

| Вопрос | Кто отвечает | Тип |
|---|---|---|
| «Где, по мнению модели, находится подтверждение?» | LLM | `EvidenceCandidate` |
| «Существует ли фрагмент, где именно, с какими координатами и статусом?» | Python (Evidence Resolver) | `EvidenceRecord` |

Модель предлагает **цитату и подсказки**; запись создаёт Python. У `EvidenceCandidate`
**нет** полей `char_start`, `char_end`, `bbox`, `source_sha256`, `match_status`,
`match_type`, `occurrence_index`, `page`; `extra="forbid"` отвергает любую попытку их
передать — ошибка валидации называет поле. Подсказка (`page_hint`, `section_hint`,
`block_id_hint`) — именно подсказка: резолвер вправе её подтвердить, проигнорировать или
опровергнуть, и ни одно решение не принимается только на её основании.

## 2. `EvidenceCandidate` — предложение модели

| Поле | Тип | Обяз. | Ограничения и смысл |
|---|---|---|---|
| `candidate_id` | identifier | да | `^[a-z0-9][a-z0-9_\-]{2,63}$`; уникален в пределах вызова |
| `document_id` | identifier | да | тот же шаблон; обязан совпадать с документом конверта |
| `field_path` | dotted path | да | `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`, ≤ 128 символов |
| `quote` | строка | да | 1–2000 символов; пробелы по краям срезаются |
| `page_hint` | целое или `null` | нет | ≥ 1 |
| `section_hint` | строка или `null` | нет | ≤ 256 символов |
| `block_id_hint` | строка или `null` | нет | ≤ 256; workflow сверяет его с реально выданными блоками |
| `context_before` | строка или `null` | нет | ≤ 500 символов; подсказка для устранения неоднозначности |
| `context_after` | строка или `null` | нет | ≤ 500 символов; подсказка для устранения неоднозначности |
| `confidence` | число или `null` | нет | 0.0–1.0; самооценка модели, на статус не влияет |
| `note` | строка или `null` | нет | ≤ 8192 символов, непустая |

## 3. `EvidenceRecord` — каноническое подтверждение

| Поле | Тип | Обяз. | Ограничения и смысл |
|---|---|---|---|
| `evidence_id` | identifier | да | уникален в пределах пакета; на него ссылаются поля карточки |
| `document_id` | identifier | да | документ, к которому относится подтверждение |
| `source_sha256` | sha256 | да | `^[0-9a-f]{64}$`; точная версия содержимого |
| `block_id` | строка | да | 1–256; блок канонического parsed document |
| `page` | целое или `null` | нет | ≥ 1; `null` только для источника без физической пагинации |
| `printed_page_label` | строка или `null` | нет | ≤ 256; напечатанный в журнале номер страницы (ADD §9.2) |
| `section_path` | массив строк или `null` | нет | ≤ 16 уровней, каждый непустой |
| `element_type` | enum | да | `paragraph`, `heading`, `table_cell`, `caption`, `footnote`, `list_item`, `formula`, `other` |
| `quote` | строка | да | 1–2000 символов; дословный текст источника |
| `char_start` | целое или `null` | пара с `char_end` | ≥ 0; позиция в каноническом тексте |
| `char_end` | целое или `null` | пара с `char_start` | > 0 и > `char_start` |
| `bbox` | 4 координаты или `null` | нет | `x0,y0,x1,y1`, конечные числа, `x1 > x0`, `y1 > y0`; PDF-пункты, начало координат — верхний левый угол |
| `table_ref` | `{table_id, row_index, column_index, cell_id}` или `null` | нет | только при `element_type = table_cell` |
| `occurrence_index` | целое или `null` | нет | ≥ 0; какое по счёту вхождение цитаты подтверждено |
| `extraction_method` | enum | да (по умолчанию `unknown`) | `text_layer`, `ocr`, `unknown` (ADD §9.3) |
| `match_status` | enum | да | `resolved`, `ambiguous`, `unresolved` |
| `match_type` | enum | да | `exact`, `normalized`, `fuzzy`, `none` |
| `verification_method` | enum | да | механизм сравнения, см. §4 |
| `parser_name` | строка | да | 1–256; парсер, построивший канонический документ |
| `parser_version` | строка | да | 1–256; в пакете совпадает с версией парсера запуска |
| `resolver_version` | строка | да | 1–256; версия резолвера, построившего запись |
| `created_at` | UTC datetime | да | момент построения записи |

`page` не обязателен на уровне модели, но правило пагинации
(`validate_pagination_consistency` в `src/research_platform/domain/evidence/ledger.py`)
требует `page` у каждого record пагинированного документа и запрещает её иначе.

## 4. Словарь разрешения

| `match_status` | Значение |
|---|---|
| `resolved` | ровно одно место найдено и проверено |
| `ambiguous` | совпадение более чем в одном месте, либо проверка диапазона/контекста не позволяет выбрать одно |
| `unresolved` | точного (или приемлемо нормализованного) совпадения нет |

| `match_type` | Значение | `verification_method` |
|---|---|---|
| `exact` | дословное совпадение | `exact_string_match` |
| `normalized` | совпадение после нормализации пробелов, переносов и Unicode без изменения слов | `normalized_string_match` |
| `fuzzy` | нечёткое совпадение; подтверждением не является | `fuzzy_string_match` |
| `none` | совпадения нет | `no_match_found` |

Соответствие `match_type` → `verification_method` — один к одному и проверяется кодом.

Допустимые пары `(match_status, match_type)`:

| `match_status` | `match_type` | Смысл |
|---|---|---|
| `resolved` | `exact` | дословное совпадение в единственном месте |
| `resolved` | `normalized` | совпадение после нормализации в единственном месте |
| `ambiguous` | `exact` | дословная цитата встречается несколько раз |
| `ambiguous` | `normalized` | нормализованное совпадение в нескольких местах |
| `ambiguous` | `fuzzy` | нечёткое совпадение в нескольких местах |
| `unresolved` | `fuzzy` | похожий фрагмент найден, но подтверждением не признан |
| `unresolved` | `none` | совпадения нет |

Любая другая комбинация отвергается (`_ALLOWED_PAIRS`): в частности `resolved` + `fuzzy`,
`resolved` + `none`, `unresolved` + `exact`, `unresolved` + `normalized`, `ambiguous` +
`none`. Правило словами: **нечёткое совпадение никогда не может быть отчитано как
`resolved`** — повышение `fuzzy` до подтверждения невозможно ни флагом, ни отдельным полем.

## 5. Правила, которые обеспечивает запись

1. `resolved` требует проверенного диапазона символов (`char_start` и `char_end` вместе) и
   `occurrence_index` — резолвер фиксирует, какое вхождение он проверил.
2. `unresolved` не вправе заявлять вхождение: `occurrence_index` обязан быть `null`.
3. `bbox` — позиция на физической странице, поэтому требует `page`.
4. `table_ref` допустим только при `element_type = table_cell`.
5. `char_start`/`char_end` передаются только парой, и `char_end > char_start`.
6. `match_type` и `verification_method` согласованы один к одному, а пара
   (`match_status`, `match_type`) входит в разрешённый набор (§4).
7. `parser_name` и `parser_version` записи совпадают с одноимёнными полями `run` пакета.
8. Записи принадлежат документу и его точной версии (`source_sha256`): подтверждение нельзя
   перенести на другой файл или другую версию.

## 6. `EvidenceCandidateList` — контракт структурированного вывода вызова

| Поле | Тип | Обяз. | Ограничения |
|---|---|---|---|
| `contract_version` | строка | нет | по умолчанию `2.1`, шаблон `^\d+\.\d+$` |
| `document_id` | identifier | да | документ, к которому относятся кандидаты |
| `field_group` | строка | да | 1–256 символов; группа полей одного вызова |
| `candidates` | массив `EvidenceCandidate` | нет | ≤ 200, по умолчанию пуст |

Конверт — артефакт типа `extraction_candidates`: то, что модель возвращает до запуска
резолвера; схема — `contracts/agent_1a/v2.1/evidence_candidates.schema.json`. Проверяется
кодом: кандидаты принадлежат документу конверта (чужой `document_id` — ошибка), а
`candidate_id` уникальны.

## 7. Восемь правил разрешения

Порядок работы резолвера; каждое правило оставляет след в записи.

1. **Существование блока.** Блок (`block_id`) должен существовать в каноническом parsed
   document этого документа и версии.
2. **Физическая страница.** Если документ пагинирован, страница обязана существовать и
   попадать в `1..page_count`; иначе `page` остаётся `null`.
3. **Поиск цитаты по нормализованному тексту.** Цитата ищется в нормализованном тексте
   блока; результат сравнения фиксируется в `match_type` (`exact`/`normalized`/`fuzzy`).
4. **Проверка диапазона символов.** Найденный фрагмент даёт `char_start`/`char_end`, и
   диапазон проверяется на корректность (`char_end > char_start`).
5. **Проверка окружающего контекста.** `context_before`/`context_after` — подсказки,
   которые резолвер **вправе** использовать, чтобы выбрать одно из нескольких вхождений;
   они не являются доказательством и не заменяют проверку текста.
6. **Разрешение повторяющихся фрагментов.** Если цитата встречается несколько раз,
   `occurrence_index` выбирает резолвер, а не модель.
7. **Отказ выдумывать координаты.** Если совпадение неоднозначно, резолвер не назначает
   координаты «наугад»: запись получает `ambiguous` (или `unresolved`), а не вымышленную
   позицию.
8. **Привязка к хешу оригинала.** Запись привязывается к `source_sha256` того файла, по
   которому шло разрешение; перенос на другую версию файла запрещён.

Реализация резолвера — Итерация 4 (ADD §12). В Итерации 0 контракт кодирует **последствия**
этих правил (инварианты записи, §5), а не сам алгоритм.

## 8. Повторяющиеся фрагменты: снятое противоречие

Ранее ТЗ одновременно разрешало кандидату «фрагмент/диапазон» и запрещало модели назначать
координаты. Ответ контракта 2.1: модель передаёт **только цитату** и подсказки, номера
вхождения в кандидате нет вообще. Если цитата повторяется, резолвер либо сам фиксирует
вхождение (`resolved` + `occurrence_index`), либо отказывается выбирать и возвращает
`ambiguous`. Модель никогда не поставляет номер вхождения, который трактуется как локация.

---

## 9. Чего контракт не гарантирует

* `match_status = resolved` означает «фрагмент существует в указанном месте», а **не**
  «фрагмент логически подтверждает значение поля». Смысловая поддержка — задача Agent 1B и
  человека ([контракт входа Agent 1B](agent_1b_input_contract.md)).
* `fuzzy` не является evidence: потеря отрицания, смена знака коэффициента или перестановка
  смысловых элементов возможны при высокой схожести строк.
* Отсутствие evidence не доказывает отсутствие информации: пустой retrieval не является
  доказательством, а `not_found` требует отдельного обоснования — см.
  [контракт Coverage Trail](coverage_trail.md).

## 10. Версии и состояние реализации

* **2.1 — текущий контракт.** Записи несут `match_status`, `match_type` и происхождение
  парсера/резолвера; кандидат не содержит `quote_occurrence`.
* **2.0 — замороженная история** (`src/research_platform/domain/evidence/v2_0.py`):
  `match_status` ∈ `exact`/`normalized_exact`/`fuzzy_candidate`/`unresolved`, `match_type`
  отсутствует, нет `occurrence_index` и `resolver_version`, а `verification_method` для
  неразрешённой цитаты называется `resolver_unresolved`. Эти записи существуют только как
  история: модуль не редактируется под новые требования.
* Детерминированный резолвер **не реализован**: существуют модели, инварианты и схемы.
  Заглушка не создавалась — она имитировала бы готовую функциональность.

Тесты инвариантов: `tests/unit/test_evidence_contract.py`,
`tests/contract/test_agent_1a_package.py`.
