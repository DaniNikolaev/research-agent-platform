# ADR-003. Домен и порты отделены от инфраструктуры и SDK провайдеров

- **Статус:** Accepted
- **Дата:** 2026-11-11
- **Связанные требования ТЗ:** направление зависимостей между слоями; запрет импорта инфраструктуры
  и SDK провайдеров из домена; проверка границ без внешнего архитектурного линтера
- **Связанные разделы ADD:** §7.2, §7.3, §9.2, §11.1, §21

## Контекст

ADD §7.2 задаёт логические слои, ADD §11.1 требует, чтобы доменные компоненты не импортировали SDK
конкретного провайдера напрямую, ADD §9.2 требует, чтобы внутренняя модель `ParsedDocument` не
зависела от классов Docling: Docling — адаптер инфраструктуры.

В репозитории слои материализованы как пакеты: `domain/` (`base.py`, `documents/`, `cards/`,
`evidence/`, `runs/`, `validation/`), `application/ports/` (Protocols и DTO Model Gateway),
`platform/` (дом адаптеров; реализован только `platform/contracts/`), `agents/*/contracts/`
(Agent 1A и Agent 1B). Направление зависимостей: `agents → domain + application.ports`,
`application → domain`, `platform → application.ports + domain`. Обратное запрещено.

Требуется зафиксировать одно осознанное отклонение от дерева ADD §21: provider-neutral DTO и
Protocols Model Gateway размещены в `application/ports/model_gateway/`, а не в
`platform/model_gateway/`.

## Решение

1. **Граница.** `domain` не знает ни инфраструктуры, ни провайдеров, ни файловой системы.
   `application` не импортирует `platform`, `agents`, `config`, `cli` и инфраструктурные библиотеки.
   `agents` используют домен и порты, но не `platform`.
2. **Отклонение по Model Gateway.** DTO (`ModelRequest`, `ModelResponse`, `ModelCapabilities`,
   `TokenUsage`) и Protocols (`ChatModelPort`, `StructuredOutputModelPort`, `EmbeddingModelPort`,
   `RerankerPort`, `ModelGatewayPort`) лежат в `application/ports/model_gateway/`. ADD допускает оба
   места; выбран этот вариант, потому что `platform` не должен быть импортируемым из `application` и
   `agents` — иначе порт, который реализует адаптер, оказался бы в слое адаптеров и развернул бы
   зависимость. `platform/model_gateway/` остаётся домом адаптеров провайдеров; это записано в его
   `__init__.py` вместе с требованиями к будущему адаптеру.
3. **Порты — `typing.Protocol`, не `ABC`.** Адаптер не наследует платформенный код, поэтому
   реализация в тесте (`tests/fixtures/fakes.py`) является полноправной реализацией, а не моком
   особого рода.
4. **Домен не знает путей.** Публичный контракт содержит только логические URI `artifact://…`;
   отображение в физический путь — обязанность адаптера (ADR-006).
5. **Проверка.** Границы обеспечиваются `tests/unit/test_import_boundaries.py`: AST-скан
   импортов (абсолютных и относительных) — `domain` без инфраструктуры, `domain` без
   `pathlib`/`os`/`shutil`/`tempfile` и без вызова `open()`, `application` без инфраструктуры,
   агенты без взаимных импортов, агенты без `platform`, `cli.py` как единственная точка входа;
   отдельные тесты-«стражи» проверяют, что относительный импорт разрешается в абсолютное имя и
   что `from ...platform import …` действительно детектируется.
   Внешний архитектурный линтер (import-linter, deptry) сознательно не вводится: для каркаса этого
   размера AST-тест стоит дешевле и не добавляет зависимости.

## Статус

Accepted, включая отклонение по расположению Model Gateway. Исключений из правил зависимостей в
Итерации 0 нет; любое будущее исключение обязано быть описано отдельным ADR.

## Последствия

Положительные: замена провайдера или storage-бэкенда не затрагивает контракты; домен тестируется без
сети, БД и модели; отклонение задокументировано, поэтому расхождение с деревом ADD §21 не выглядит
случайным.

Цена: `Protocol` не проверяется при импорте, поэтому соответствие адаптера порту ловится только
тестами и `runtime_checkable`; агенты и домен не могут использовать инфраструктурные удобства
(например, `pathlib` в домене) даже там, где это было бы короче; синхронные порты ограничивают
будущую асинхронность.

## Альтернативы

- **Разместить Model Gateway в `platform/model_gateway/` (как в ADD §21).** Отклонено: `application`
  и `agents` импортировали бы слой адаптеров, что и есть инверсия зависимости. ADD прямо допускает
  оба варианта, поэтому это отклонение, а не нарушение.
- **Внешний линтер зависимостей.** Отклонено для Итерации 0; пересмотреть, когда модулей станет
  заметно больше или появится первое исключение.
- **`ABC` и наследование вместо `Protocol`.** Отклонено: связывает адаптеры с версией платформенного
  кода и мешает подмене в тестах.

## Открытые риски

1. `imported_modules()` разрешает относительные импорты (`from ...platform import x`)
   против пакета импортирующего модуля, и это покрыто отдельным тестом
   (`test_relative_import_of_platform_is_detected`). Остаточный зазор: динамический
   импорт (`importlib.import_module(...)`, `__import__(...)`) AST-скан не видит.
   Закрывать при появлении первого динамического импорта. Владелец: архитектор.
2. Правило «`platform` реализует порты, обратная зависимость запрещена» проверено только в одну
   сторону: тест запрещает `platform` в `application`, но не проверяет, что у каждого порта есть
   адаптер.
3. Запрет «домен не знает про файловую систему» не покрывает сеть и часы: `datetime.now()` в домене
   тестом не запрещён, хотя время должно приходить снаружи как `UtcDatetime`.
