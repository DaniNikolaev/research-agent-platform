# ADR-008. Детерминированный Evidence Resolver на стороне Python

- **Статус:** Accepted (контракт 2.1) / Deferred (реализация резолвера — Итерация 4)
- **Дата:** 2026-11-12
- **Связанные требования ТЗ:** провенанс evidence; запрет модели назначать координаты и статус совпадения;
  связь карточки с ledger
- **Связанные разделы ADD:** §6.1, §9.3, §12.1–§12.5, §22 (этап 4)

## Контекст

ADD §12.1 формулирует ключевое решение: LLM не является авторитетным источником координат evidence.
Модель может вернуть кандидата — цитату и подсказки; Python Evidence Resolver проверяет кандидата на
исходном `ParsedDocument` и только после этого создаёт канонический объект. ADD §12.4 добавляет:
`evidence_id`, страница, span, hash и match status выставляются Python.

В репозитории это реализовано структурно: `EvidenceCandidate` не имеет полей координат, хеша, статуса
и вхождения, а `extra="forbid"` отвергает попытку их передать. Прежнее напряжение ТЗ — кандидат может
содержать «фрагмент/диапазон», но модели запрещено назначать `char_start`/`char_end` — **закрыто
контрактом 2.1**: кандидат несёт только текст цитаты и подсказки, а поле `quote_occurrence` удалено,
чтобы порядковый номер от модели нельзя было принять за локацию. Это документирует прежнюю
неоднозначность, а не открытое решение; подтверждение заказчика больше не требуется.

## Решение

1. **`EvidenceCandidate` — только предложение модели.** Поля: `candidate_id`, `document_id`,
   `field_path`, обязательный `quote` (1–2000 символов), необязательные подсказки `page_hint`,
   `section_hint`, `block_id_hint`, `context_before`/`context_after` (до 500 символов каждая),
   `confidence`, `note`. Координат, хеша, статуса и `occurrence` нет; подсказки названы hint намеренно
   и не имеют доказательной силы.

2. **`EvidenceRecord` — проверенный результат резолвера.** Поля: `evidence_id`, `document_id`,
   `source_sha256`, `block_id`, `page`, `section_path`, `element_type`, `quote`, `char_start`/`char_end`,
   `bbox`, `table_ref`, `occurrence_index`, `extraction_method`, `match_status`, `match_type`,
   `verification_method`, `parser_name`, `parser_version`, `resolver_version`, `created_at`
   (а также необязательный `printed_page_label`).

3. **Словарь статусов закрыт.** `match_status` ∈ `resolved` / `ambiguous` / `unresolved`;
   `match_type` ∈ `exact` / `normalized` / `fuzzy` / `none`; `verification_method` выводится из
   `match_type` один-к-одному. `fuzzy` никогда не даёт `resolved`; `ambiguous` — полноценный исход для
   повторяющихся или неоднозначных совпадений, а не ошибка резолвера.

   | `match_status` | `match_type` | `verification_method` |
   |---|---|---|
   | `resolved` | `exact` / `normalized` | `exact_string_match` / `normalized_string_match` |
   | `ambiguous` | `exact` / `normalized` / `fuzzy` | соответствующий строковый метод |
   | `unresolved` | `fuzzy` / `none` | `fuzzy_string_match` / `no_match_found` |

4. **Восемь правил разрешения.**
   1. Подсказки кандидата не являются локатором: резолвер ищет `quote` в каноническом тексте;
      `page_hint`/`section_hint`/`block_id_hint` могут лишь сузить поиск.
   2. Порядок сопоставления — `exact`, затем `normalized`, затем `fuzzy`; выбранный механизм
      фиксируется в `verification_method`.
   3. Единственное exact/normalized совпадение даёт `resolved`; резолвер сам записывает `block_id`,
      `page`, `section_path`, `char_start`/`char_end` и `occurrence_index`.
   4. Несколько совпадений или неоднозначный контекст дают `ambiguous`; резолвер не выбирает позицию
      произвольно. Если контекст позволяет однозначно выбрать вхождение, он фиксирует
      `occurrence_index`, иначе запись остаётся `ambiguous`.
   5. Нет exact/normalized совпадения: fuzzy-сходство даёт `ambiguous`/`fuzzy` или
      `unresolved`/`fuzzy`, а при отсутствии приемлемого сходства — `unresolved`/`none`.
   6. `fuzzy` никогда не даёт `resolved`: допустимы только `ambiguous`+`fuzzy` и `unresolved`+`fuzzy`.
   7. `resolved` требует проверенного `char_start`/`char_end` и `occurrence_index`; `unresolved` не
      имеет права заявлять `occurrence_index`; `char_start`/`char_end` — только парой, `char_end > char_start`.
   8. `bbox` требует `page`; `table_ref` — только для `element_type="table_cell"`;
      `source_sha256` и provenance парсера/резолвера фиксируют версию источника и инструментов.

5. **Карточка ссылается, а не копирует.** Поле содержит `evidence_refs[]` с `evidence_id`;
   денормализованные `quote`, `page`, `section_path` — read-only копии, и `validate_card_references()`
   требует их точного равенства ledger. Ledger — единственный источник истины.

## Статус

Accepted для контракта 2.1: модели и инварианты реализованы и покрыты
`tests/unit/test_evidence_contract.py`, `tests/contract/test_agent_1a_package.py`,
`tests/unit/test_card_field_rules.py`. Резолвер (сопоставление, нормализация, fuzzy-порог, таблицы) —
**Deferred** до Итерации 4 (ADD §22, этап 4). Вопрос о прочтении ТЗ закрыт структурно.

## Последствия

Положительные: подделка координат структурно невозможна; подсказки не смешиваются с фактами; ledger
самодостаточен и проверяем офлайн; карточка и ledger не могут разойтись незаметно.

Цена: резолвер обязан реализовать нормализацию и fuzzy-порог, иначе `unresolved`/`ambiguous` станут
массовыми; два типа требуют преобразования; `ambiguous` требует отдельной downstream-политики.

## Альтернативы

- **Модель возвращает готовый evidence record.** Отклонено: ровно то, что запрещает ADD §12.1; страница
  и статус совпадения стали бы утверждениями модели.
- **Постфактумный поиск цитаты по карточке.** Отклонено: карточка не содержит контекста цитаты, поиск неоднозначен, `block_id` теряется.
- **Только ручная проверка человеком.** Отклонено как единственный механизм: не масштабируется и не
  даёт детерминированного статуса; человек остаётся обязательным для смысловой поддержки (ADD §12.5).

## Открытые риски

1. Порог fuzzy-сопоставления и правила нормализации (пробелы, переносы, Unicode, дефисы) не определены;
   без них `normalized` и `fuzzy` не воспроизводимы между прогонами. Владелец: архитектор, Итерация 4.
2. Резолвер не реализован: поведение на реальных PDF (колонки, таблицы, OCR-страницы) не проверено.
3. `resolved` подтверждает существование фрагмента, но не смысловую поддержку значения (ADD §12.5);
   потребитель может прочитать статус шире, чем он есть.
4. Контракт не запрещает ссылаться из `found` на `ambiguous`-запись; workflow не должен трактовать её как подтверждение.
